# Zodo：DSH 日程插件开发路线

本分支从 `42075df` 开始独立迭代。目标不是复制一套通用生产力平台，而是让 DSH 用户每天打开 Zodo，就能回答三个问题：接下来要做什么、今天还有多少可安排时间、变化以后怎么调整不伤及既有承诺。DSH 是唯一正式 UI，Rust Core 仍是唯一事实与审批来源。

## 产品取舍

- 首屏给出下一项、今日已定日程和待安排任务。不要求先选模型、建项目或连日历。先把人工操作做顺，再加 AI 提议。
- 手动固定预约、日历导入忙碌和可移动任务分配明确区分。看不到数据、数据过期和没有事件不能都叫「空闲」。
- 计划先展示拟移动内容与原因，写入沿用 Core 的 revision / explicit approval / receipt；不移动已经开始、过去或锁定的事项，不为凑满日程制造建议。
- 默认本地使用。外部忙碌字段最小化；不把私人标题送进模型，无授权不联网、发提醒或写第三方日历。不为 v1 增加第二套 UI 或日历双向同步。

## 迭代顺序

1. **可信日程**：可前后浏览和回到今天；同一时间轴按本地显示日期与实际时间排序，跨午夜和 DST 不误归类。添加可区分、不泄露标题的导入忙碌提示；导入缺失/过期时不误导。先验证现有预约、容量、任务编辑入口无回归。
2. **快速安排**：用日期和最少字段直接添加预约/安排任务；保存后能找回它，取消、冲突、重复点击和失败明确可恢复。Core 继续负责业务写入。
3. **可解释重排**：只在用户确认后应用；把会变、不变、放不进去的项目分开。验证陈旧版本、审批撤销和锁定预约。
4. **交付与复核**：轻量初次使用、可访问键盘路径、适配窄窗口、空/错/加载状态。先做当前版在隔离 Linux 的安装、使用、同版本重启和卸载；官方 DSH Web（Linux）、模拟 Host 与原生 Desktop 的证据分别记录。

## 完成标准

- 人面对合成的一周，能不启用 AI 完成「录入 → 看日程 → 调整 → 处理冲突」；不用理解 Core 概念，也不丢预约/已确认事实。
- 使用已导入和没有导入两种合成数据，覆盖时区、日期边界、过期状态、失败和取消。核心与适配器的自动回归通过。
- 用隔离 DSH Web profile 复核 Linux 当前版的生命周期与交互。Windows 官方桌面暂缓，不阻塞功能迭代。现阶段未正式投入使用，允许不向后兼容的 API、配置和数据格式变更；不把旧版迁移、跨版本升级或回退列为当前目标。当前版同版本数据持久性仍须验证。功能先在 `xiaoz/zodo-scheduler` 独立验证，再通过面向 `main` 的 PR 整体集成前端、Core 和回归测试。合并不等于发布；CI 只用隔离环境与合成数据。
