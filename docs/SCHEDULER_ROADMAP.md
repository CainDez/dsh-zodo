# Zodo：DSH 日程插件开发路线

本分支从 `42075df` 开始独立迭代。目标不是复制一套通用生产力平台，而是让 DSH 用户每天打开 Zodo，就能回答三个问题：接下来要做什么、今天还有多少可安排时间、变化以后怎么调整不伤及既有承诺。DSH 是唯一正式 UI，Rust Core 仍是唯一事实与审批来源。

## 产品取舍

- 首屏给出下一项、今日已定日程和待安排任务。不要求先选模型、建项目或连日历。先把人工操作做顺，再加 AI 提议。
- 手动固定预约、日历导入忙碌和可移动任务分配明确区分。看不到数据、数据过期和没有事件不能都叫「空闲」。
- 计划先展示拟移动内容与原因，写入沿用 Core 的 revision / explicit approval / receipt；不移动已经开始、过去或锁定的事项，不为凑满日程制造建议。
- 默认本地使用。外部忙碌字段最小化；不把私人标题送进模型，无授权不联网、发提醒或写第三方日历。不为 v1 增加第二套 UI 或日历双向同步。

## 迭代顺序

1. **可信日程**：可前后浏览和回到今天；同一时间轴按本地显示日期与实际时间排序，跨午夜和 DST 不误归类。添加可区分、不泄露标题的导入忙碌提示；导入缺失/过期时不误导。先验证现有预约、容量、任务编辑入口无回归。
2. **快速安排**：用日期和最少字段直接添加预约/安排任务；保存后能找回它，取消、冲突、重复点击和失败明确可恢复。Core 继续负责业务写入。
3. **可解释重排**：只在用户确认后应用；把会变、不变、放不进去的项目分开。验证陈旧版本、审批撤销和锁定预约。
4. **交付与复核**：轻量初次使用、可访问键盘路径、适配窄窗口、空/错/加载状态。先做当前版在隔离 Linux 的安装、使用、同版本重启和卸载；官方桌面与浏览器模拟的验收分别记录。

## 完成标准

- 人面对合成的一周，能不启用 AI 完成「录入 → 看日程 → 调整 → 处理冲突」；不用理解 Core 概念，也不丢预约/已确认事实。
- 使用已导入和没有导入两种合成数据，覆盖时区、日期边界、过期状态、失败和取消。核心与适配器的自动回归通过。
- 用隔离 DSH Web profile 复核 Linux 当前版的生命周期与交互。Windows 官方桌面暂缓，不阻塞功能迭代。现阶段未正式投入使用，允许不向后兼容的 API、配置和数据格式变更；不把旧版迁移、跨版本升级或回退列为当前目标。当前版同版本数据持久性仍须验证。所有变更只提交到 `xiaoz/zodo-scheduler`，不合并、不发布、不动真实数据。

## 进度（实现与验收分开）

| 范围 | 分支实现及已验证证据 | 仍需验证 |
| --- | --- | --- |
| 可信日程 | 日期导航、本机时间轴、午夜和 DST、脱敏忙碌与新鲜度进入适配器；合成回归覆盖纯逻辑和只读行为。 | Windows Chrome 夹具已验证渲染和窄窗导航；Linux 真实 DSH Web 渲染仍需检查有／无忙碌覆盖和过期状态。 |
| 快速安排 | 固定预约、任务日期、安排具体时段分开；候选按工作空间日期筛选；指定时段必须用 Core 严格提案。真实 HTTP 冒烟验证预览和批准不新增分配，提交只新增一条；官方 DSH Web 已通过界面录入任务，且刷新后保留同一 ID、估时和 revision。 | 官方 Web 验证按指定窗口安排任务、调整以及冲突；丢失回执恢复目前只在模拟 Host 验证。 |
| 可解释重排 | 默认只追加；明确选重排才允许移动未来未锁定安排。Core 回归验证审批绑定的删除集合和候选开始时间漂移会拒绝提交。手动删除或修改只作用于未来未锁定的计划分配，提交时再次判断原时段是否已经开始。 | 在 Linux 真实 DSH Web 中用同一组固定承诺对照验证两种模式。 |
| 交付与复核 | Linux x64 打包及官方 Web 干净安装、Core 联动、双重启、卸载已做 HTTP/生命周期冒烟。官方 Web 真实界面通过首次使用、两页 Enter/Esc 取消、新建任务与刷新。同一源码的模拟 Host 为 34/34，详见宿主验收记录。 | 在官方 Web 验证实际排程、窄窗口、完整一周流程，并复核当前版本进程重启。原生 Windows Desktop 暂缓。 |

分支尚未通过最终验收。命令、精确版本和已知环境限制见[宿主验收门槛](SCHEDULER_HOST_ACCEPTANCE.md)。
