# 清晰日程界面文案基线

| 位置 | 实施文案与行为 |
| --- | --- |
| D01 两项建议摘要 | “建议调整以下两项弹性事务，为下午留出空闲。”计数来自当前提案，不硬编码 |
| D02 未选择提醒时间 | 字段“未确定”；候选不是已保存的提醒 |
| D02 选中15:00 | 字段“15:00 · 待保存”；保存后再显示回执，不靠高亮暗示生效 |
| 目标日期 | “期望完成”；硬期限另标“必须完成”，不能混用 |
| 提案 | “待你确认”或“尚未应用”；动作“确认应用”“继续调整”“放弃预览” |
| 生成中 | 保留输入，显示阶段并可取消；不显示“已保存” |
| 提案过期 | “计划依据已变化，请重新检查。”不能重放旧批准 |
| 提交结果未知 | “正在核对保存结果”；查询同一操作回执，不能盲目再建任务 |
| 专注结束 | “记录本次进度”；任务完成另行选择 |
| 回顾 | 实际45分钟、剩余约45分钟，只建议下一次45分钟；不重复计算已投入 |
| 本地模型不可用 | “本地模型暂不可用，草稿已保留。”提供准备模型或手工处理；云端需符合策略并取得相应许可 |
| 外部助理授权 | 显示可读对象/字段、可提议或提交范围及流向；“本地处理”不自动保证外部agent也不外发 |

按钮避免泛用“确定”。不使用可靠度百分比代替澄清和权限，不写“AI已完全理解”或未经检验的最佳安排。正文和状态文案应可本地化，不能把中文字符串作为领域枚举值。


## Harness首期文案

旧图中的“本地处理”“模型已就绪”仅为参考状态。新界面分别展示Host、Core和模型的实际处理位置；宿主工具许可与业务“确认应用”分开，前者不写成后者已经批准。五业务入口在插件内组织，未验证的原生通知和后台能力不显示为已支持。
